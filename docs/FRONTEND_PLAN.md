## 1. Goals and non-goals

**Goals**
1. One SPA, five personas (Customer, Merchant, Courier, Dispatcher, Admin), plus a public tracking page.
2. A demo that never shows a blank screen. Every API failure renders as a readable RFC 7807 message.
3. The public `/track/:tn` page is mobile-first, updates live, and scores Lighthouse mobile ≥ 90. The marker will open this page.
4. The courier screen works one-handed on a phone over the LAN.
5. Contract drift breaks the build, using types generated from the gateway's OpenAPI.

**Non-goals:** native apps, i18n, offline/PWA, SSR, a custom design system beyond shadcn/ui.

## 4. Cross-cutting architecture

### 4.1 Runtime config (one image for Compose and Kubernetes)

`VITE_*` variables are baked in at build time. That would force a separate image per environment and would break `PLT-3`. Use a runtime file instead:

- `public/config.js` defines `window.__SWIFTDROP__ = { apiBaseUrl, wsUrl, assistantEnabled }` and is loaded by `index.html` **as an external script**, which keeps it CSP-safe with no inline script.
- In the container, `40-runtime-config.sh` rewrites it from `API_BASE_URL`, `WS_URL` and `ASSISTANT_ENABLED` using `envsubst`.
- `src/config/env.ts` reads `window.__SWIFTDROP__` first and falls back to `import.meta.env.VITE_API_BASE_URL` (default `http://localhost:8081`).
- `nginx.conf` serves `config.js` with `Cache-Control: no-store`.

### 4.2 API client (`api/client.ts`)

One `request()` function. Every endpoint module calls it.

1. Prefixes `apiBaseUrl`, sets `credentials: 'include'` so the refresh cookie flows, and sets `Accept: application/json, application/problem+json`.
2. Attaches `Authorization: Bearer <access>` from `tokenStore` when present.
3. Sends `X-Request-Id: crypto.randomUUID()` so the id is known even when the response is lost.
4. **On a 401** (not on `/auth/*`), it awaits `tokenStore.refresh()`, which is single-flight: concurrent 401s share one promise. It then retries the original request **once**. If the refresh fails, it clears the session and redirects to `/login?returnTo=…&reason=expired`.
5. Non-2xx responses are parsed into `ApiError { status, errorCode, title, detail, violations[], traceId, retryAfter? }`. A non-problem body becomes `INTERNAL_ERROR` with the status preserved.
6. `204` returns `undefined`. Blob endpoints (receipt PDF) use `requestBlob()`, which follows the same auth and refresh rules.

### 4.3 Error UX: one mapping, used everywhere

| `errorCode` | UI behaviour |
|---|---|
| `VALIDATION_FAILED` | `violations[]` → `form.setError(field, …)`, plus a summary toast if a field is not on the form |
| `INVALID_CREDENTIALS` | Inline "Email or password is incorrect" on the login form |
| `UNAUTHENTICATED` | Handled by the refresh flow. If refresh fails, redirect to login |
| `ACCESS_DENIED` | `/403` page for route-level failures; toast for action-level failures |
| `MERCHANT_NOT_APPROVED` | Redirect to `/merchant/pending` |
| `RESOURCE_NOT_FOUND` | `<ErrorState variant="not-found">` (on pricing: "We don't deliver there yet") |
| `CONFLICT` / `INVALID_STATUS_TRANSITION` | Toast with `detail`, then refetch the affected query |
| `RATE_LIMITED` | Disable the submit button and show a countdown from `Retry-After` |
| `UPSTREAM_UNAVAILABLE` | Banner: "Part of SwiftDrop is temporarily unavailable", with a Retry button |
| any | Every error state shows `traceId` in small text with a copy button, for debugging with backend owners |

Also: a route-level `errorElement` plus a top-level `ErrorBoundary` that renders a "Something went wrong" card with a reload button.

### 4.4 Auth state (`auth/`)

- The **access token lives in memory only** (module variable plus React context). Never in `localStorage` or `sessionStorage`.
- **Boot sequence:** `AuthProvider` calls `POST /api/v1/auth/refresh` once on load. On success it stores the token and fetches `GET /users/me`. On a 401 the visitor is anonymous. A full-screen splash shows until this resolves, so guards never flash the wrong page.
- Claims (`sub`, `email`, `roles`, `merchantId`, `exp`) are decoded client-side **for display and routing only**. The server always authorizes.
- A proactive refresh timer fires 60 s before `exp`. The 401 handler is the safety net.
- **Logout** calls `POST /auth/logout`, clears the token, runs `queryClient.clear()`, and navigates to `/login`.
- **Role landing** after login: ADMIN → `/admin`, DISPATCHER → `/admin/dispatch`, COURIER → `/courier/today`, MERCHANT → `/merchant/orders`, CUSTOMER → `/deliveries`. Honour `returnTo` if present **and** it is a relative path (open-redirect guard).

### 4.5 Data fetching conventions

- Query keys come from `queryKeys.ts` only, e.g. `qk.parcels.list(filters)` and `qk.parcels.detail(id)`.
- List filters live in the **URL search params** (`?status=IN_TRANSIT&page=2`). This makes them shareable, keeps the back button working, and survives reload.
- Defaults: `staleTime` 30 s, `retry` 1 (never retry 4xx), `refetchOnWindowFocus` on for operational screens (dispatch board, courier today).
- Mutations invalidate exact keys. Optimistic updates are used **only** on the courier status advance, with rollback on error.

### 4.6 Realtime ladder (`realtime/useParcelLiveStatus.ts`)

```
STOMP over SockJS  /ws  →  subscribe /topic/parcels.{tn}
   │ connect fails or drops 3× within 60 s
   ▼
SSE  GET /api/v1/tracking/{tn}/stream
   │ error / unsupported
   ▼
Polling  GET /api/v1/tracking/{tn}  every 15 s
```

- Each pushed message is written straight into the TanStack cache (`setQueryData(qk.tracking.public(tn))`), so the UI only ever reads from the query.
- The hook exposes `connection: 'live' | 'sse' | 'polling' | 'offline'`, and the page shows a small "Live" dot.
- Reconnect uses exponential backoff with jitter. The hook pauses when `document.hidden` and resumes with an immediate refetch.
- The STOMP and SockJS libraries are `import()`ed lazily, so they don't weigh down the main bundle.

### 4.7 Design system

- shadcn/ui primitives: Button, Input, Select, Dialog, Sheet, Table, Tabs, Badge, Card, Toast, DropdownMenu, Skeleton, Switch, Tooltip, Form.
- **Status palette**, defined once in `StatusChip`:

| Status | Color | Icon |
|---|---|---|
| `CREATED` | slate | `PackagePlus` |
| `PICKED_UP` | blue | `PackageCheck` |
| `IN_TRANSIT` | indigo | `Truck` |
| `OUT_FOR_DELIVERY` | amber | `Bike` |
| `DELIVERED` | green | `CircleCheck` |
| `FAILED` | red | `CircleAlert` |
| `CANCELLED` | zinc, struck-through | `Ban` |

- **Money:** `MoneyLKR` uses `Intl.NumberFormat('en-LK', { style: 'currency', currency: 'LKR' })`. Values arrive as strings or decimals. Never do float arithmetic in the UI, only display.
- **Phone:** inputs enforce `+94XXXXXXXXX`. A display helper masks to the last 3 digits where needed.
- **Accessibility:** every form field has a label, focus rings stay visible, colour is never the only signal (chips carry an icon and text), touch targets are ≥ 44 px on courier and tracking screens, and `jsx-a11y` lint is clean.
- **Theme:** light only, orange and white. There is no dark mode and no theme toggle. The brand colour is a single CSS variable (`--primary` in `src/index.css`), so changing it is a one-line edit; keep it dark enough for white text (contrast ≥ 4.5:1).

## 7. Screen specifications

Every screen implements the four states: **loading** (skeleton, not a spinner, for lists), **empty** (illustration, a sentence, and a primary action), **error** (`ErrorState` with retry and `traceId`), and **success**.

### 7.1 Auth — FE-2

Sign-in, sign-up and the Google callback render **full screen** in `AuthShell`: no sidebar, no top bar, no assistant button. A brand panel sits beside the form on wide screens and collapses to a small logo on phones.

**Login**
- Fields: email and password, both required. The form shows the same error for a wrong email and a wrong password.
- "Continue with Google" button. A "Session expired, please sign in again" banner when `?reason=expired`.
- A 429 disables the button with a countdown.

**Signup**
- Zod schema matching IDN-1:
  - email
  - password ≥ 8 characters, containing a letter and a digit (with a live checklist)
  - full name
  - phone `^\+94\d{9}$` (with a `+94` prefix adornment)
- A 409 maps to "An account with this email already exists" with a link to `/login`.

**OAuth callback**
- Reads `code` and `state`, verifies `state` against `sessionStorage`, then exchanges.
- On mismatch, error or 409 (Google already linked elsewhere), shows a clear explanation and a "Back to login" link.
- On success, goes to the role landing page.

**Forbidden (403)** names the required role and links to the user's own home.

### 7.2 Customer — FE-3

**`/deliveries/new`, the booking form**
- Sections:
  1. Pickup (contact name, phone, line 1, line 2, city, postal code)
  2. Drop-off (same fields)
  3. Parcel: size as a segmented control (SMALL / MEDIUM / LARGE, each with a size hint), weight in kg (step 0.1, > 0), express toggle
- City is a combobox fed by the zone city list (C9), with free text allowed.
- **Live estimate panel** (sticky on desktop, bottom sheet on mobile):
  - Fires once city, city, size and weight are valid, debounced 400 ms.
  - Uses `useQuery(qk.pricing.estimate(input))` so identical inputs come from cache.
  - Shows zone from → to, base fee, weight surcharge, express surcharge and **total LKR**.
  - A 404 shows "We don't deliver to {city} yet". A 400 maps to the weight field. A 503 shows "Pricing is unavailable, you can't book right now" and disables submit.
- Submit → `POST /parcels` → success dialog with the **tracking number**, plus Copy, Share (`navigator.share`, falling back to copying the link), "View delivery" and "Book another".
- Submit is disabled while the estimate is loading or stale for the current inputs.
- A "Use my details" button copies the profile name and phone into the pickup contact.

**`/deliveries`, my parcels**
- Columns: tracking number, created date, from → to cities, size, fee and status chip.
- Filters: status (multi), date range. Pagination. Sort by newest.
- Rows link to the detail page. On mobile, the table becomes cards.
- Empty state: "No deliveries yet" with a "Book your first delivery" button.

**`/deliveries/:id`, detail**
- Header: tracking number (copy), status chip, Share tracking link, Download receipt (`requestBlob` → `URL.createObjectURL` → `a.download`).
- Status timeline from `/history`, newest first, showing actor and note. A `FAILED` entry shows `failureReason` prominently.
- Pickup and drop-off cards, plus a fee breakdown card.
- Proof-of-delivery image (presigned URL) with a lightbox, shown when `DELIVERED`.
- **Cancel** button, shown only when the status is `CREATED`, behind a confirm dialog. A 409 refetches and shows a toast.
- Subscribes to live updates with `useParcelLiveStatus`, so an open detail page also updates.
- A 404 shows "This delivery doesn't exist or isn't yours", without distinguishing the two cases.

### 7.3 Public tracking — FE-3 (the marker's screen)

**`/track`** shows one large input with format hint `SD-XXXXXXXX`, auto-uppercases, and validates `^SD-[A-HJ-NP-Z2-9]{8}$` before navigating.

**`/track/:trackingNumber`** uses `PublicShell` only: a small logo and nothing else.
- Hero: the large status label, an icon, "Updated 2 min ago", and a "Live" connection dot.
- Route line: **origin city → destination city**, plus ETA. No addresses, phones or names beyond the courier's first name.
- Horizontal progress stepper (CREATED → … → DELIVERED). FAILED and CANCELLED render as a branch state.
- Vertical timeline with local times.
- Share button and "Track another".
- 400 → "That doesn't look like a SwiftDrop tracking number". 404 → "We couldn't find that parcel", the same message whatever the reason. 429 → "Too many lookups, try again in Ns".
- **Performance budget:**
  - The route is code-split and does not import the app shell, TanStack devtools, Recharts or shadcn Table.
  - Initial JS for this route ≤ 90 KB gzip. STOMP and SockJS load after first paint.
  - System font stack, no web fonts. SVG icons only.
  - `<meta name="theme-color">`, a proper `<title>Tracking SD-… · SwiftDrop</title>`, and an OG description.
- Lighthouse mobile ≥ 90 on Performance, Accessibility, Best Practices and SEO, verified at 360 px.

### 7.4 Merchant — FE-4

**Register.** Fields: org name, business registration number, contact email, contact phone. A 409 means "You already have a merchant application", with a link to Pending.

**Pending.** Shows a status card (PENDING / REJECTED / SUSPENDED) with explanatory copy and polls every 60 s. Once APPROVED, it prompts "Sign out and back in to activate merchant features", because the new role arrives in the next token (or it triggers a token refresh, if the refresh endpoint re-reads roles; ask Amandi).

**Orders.**
- Table: merchant reference, tracking number, created date, destination city, status. Filters, plus search by reference.
- **New order** is the booking form reused (`features/customer/BookingForm` refactored into `components/booking/`), with an extra "Your reference" field.

**API keys.**
- List: prefix `sk_live_ab12cd34…`, label, scopes, last used, expiry, and Revoke (confirm dialog).
- **Generate** asks for a label and scopes, then opens the **`CopyOnceModal`**:
  - The full key sits in a monospace read-only field with a Copy button.
  - A red callout reads "You will not see this key again".
  - The "Done" button stays disabled until the user ticks "I have copied this key".
  - Closing the modal wipes the key from component state and the query cache. **The key must never enter TanStack cache or logs.**

**Webhook.**
- URL input with client-side `https://` validation (the server also applies the SSRF guard).
- Saving returns the secret, shown in the same `CopyOnceModal`.
- A "Verifying signatures" card with tabbed code snippets (Node, Python, Java) for `X-SwiftDrop-Signature: t=…,v1=…`.

**Webhook deliveries.**
- Table: event id, tracking number, URL, attempts, last status, state (PENDING / DELIVERED / DEAD) and next retry.
- Expanding a row shows the attempt history. Replay requires confirmation and then refetches.

### 7.5 Courier — FE-4 (phone-first)

**`/courier/today`**
- Top bar: today's date, a count summary ("6 to deliver · 2 done · 1 failed") and pull-to-refresh, implemented as a refresh button plus refetch-on-focus.
- Assignment cards **grouped by pickup city**, then drop-off city (manifest order). Each card shows the tracking number, status chip, the relevant address (pickup before pickup, drop-off after), a tap-to-call phone link (masked before pickup, per PAR-4), and size and weight.
- **One big primary button** with the next legal action:

| Current status | Primary button | Then |
|---|---|---|
| `CREATED` | "Picked up" | → `PICKED_UP` |
| `PICKED_UP` | "In transit" | → `IN_TRANSIT` |
| `IN_TRANSIT` | "Out for delivery" | → `OUT_FOR_DELIVERY` |
| `OUT_FOR_DELIVERY` | "Delivered" (opens proof sheet) + secondary "Failed" | → `DELIVERED` / `FAILED` |
| `FAILED` | "Re-attempt" | → `OUT_FOR_DELIVERY` |

- **Delivered sheet:**
  - `<input type="file" accept="image/jpeg,image/png" capture="environment">` opens the camera directly on phones.
  - Client-side checks: type and ≤ 5 MB. Images larger than 1600 px are downscaled on a canvas before upload, to save mobile data.
  - Preview plus an optional note.
  - Uploads the proof first (`POST /proof`), then the status `PATCH` with `proofUrl`. Shows progress, and a retry if either step fails.
- **Failed sheet:** quick-pick reasons (Recipient unavailable, Wrong address, Refused, Unsafe location, Other with free text). The reason is required.
- The optimistic status update rolls back on 409 and shows "This parcel was updated elsewhere".
- Layout: everything reachable with the thumb (bottom-anchored actions), 48 px targets, high contrast.

### 7.6 Dispatcher / Admin — FE-4

**Dashboard (`/admin`)**
- KPI tiles: parcels today, unassigned, out for delivery, delivered today, failed today, pending merchants.
- Links into each board. A tile for an upstream that is down shows "unavailable" instead of failing the whole page (C16).

**Dispatch board (`/admin/dispatch`)**
- The unassigned queue (oldest first) with a pickup-zone filter. Each row shows age as "3 h ago" (amber after 4 h, red after 24 h), pickup city, size and weight.
- Each row has **suggested courier chips** (`GET /dispatch/suggest?parcelId`, top 3, fetched lazily when the row is visible or expanded) with the reason in a tooltip. Clicking a chip assigns.
- "Assign…" opens a courier picker: searchable, showing remaining capacity, with inactive or full couriers disabled.
- A 409 for an already-assigned parcel offers "Reassign?" (re-calls with `?reassign=true`).
- Side panel: a compact workload list, so dispatchers can see capacity while assigning.
- Auto-refresh every 15 s while the page is visible.

**Workload.** Per courier: active, delivered today, failed today, remaining capacity (with a bar). Sortable. Links to the courier's manifest.

**Couriers.**
- Registry table: name, vehicle, home zone, max daily load, active.
- Register courier: search an identity user (`GET /users?role=COURIER`), then set vehicle, zone and load.
- Edit happens in a sheet. Deactivating with open assignments shows a 409 listing the tracking numbers.

**Parcels (all).** Global parcel search by tracking number, status or date, with manual status change via the same transition rules as the courier screen. FAILED requires a reason.

**Users.**
- Table filterable by role and status, with search.
- Row actions: suspend or reactivate (confirm; warns that it signs the user out everywhere), and edit roles with checkboxes.
- The current admin's own ADMIN checkbox is disabled, with a tooltip explaining the lockout guard.

**Merchants.** Tabs: Pending, Approved, Suspended, Rejected. Approve, reject or suspend, each with a confirm dialog and an optional note. Rows show who acted and when.

**Zones.**
- Table: name, code, cities (as chips), active. Create and edit in a dialog with a tag input for cities.
- Delete gives a 409 when the zone is referenced, and suggests "Deactivate instead". An "Include inactive" toggle shows deactivated zones.

**Pricing rules.**
- Filter by size band, then show a **matrix view**: zones × zones, each cell showing base fee and per-kg. Clicking a cell edits the rule in a dialog with `effectiveFrom` and `effectiveTo`.
- A list view is also available. Fee fields are validated as non-negative with 2 decimal places.

**Reports.**
- Date range, defaulting to the last 14 days.
- A stacked bar chart of created, completed and failed per day, plus a totals row.
- **Export CSV** is generated client-side from the same data, with the header `date,created,completed,failed` and ISO dates. RFC 4180 quoting is unit-tested.

**Notification log (stretch).** Filters for status, channel and date. Resend button.

### 7.7 AI chat widget — FE-4

- A floating button at the bottom right on authenticated routes, opening a 380 px panel (full screen on mobile). Hidden entirely when `assistantEnabled=false`, or after the first 503 from `/assistant`.
- The message list streams tokens over `fetch` + `ReadableStream` (C15), with a "Stop" button that calls `AbortController`.
- **Tool-call chips** under assistant messages, e.g. `🔧 estimateFee` and `🔧 getParcelByTrackingNumber`, expandable to show the arguments.
- Text is rendered as **plain text with safe markdown** (react-markdown with no raw HTML and links set to `rel="noopener noreferrer"`). Never `dangerouslySetInnerHTML`.
- `conversationId` is kept in `sessionStorage` and rehydrated via `GET /conversations/{id}`. "New chat" calls `DELETE`.
- 2 000-character counter. A 429 shows "You've reached the hourly message limit".
- Suggested prompts on an empty chat: "How much to send 2 kg from Colombo to Kandy?", "Where is SD-…?", "Show my parcels in transit".
